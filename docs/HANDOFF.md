# HANDOFF.md — دليل Ghadir OS (ملاحظات التطوير) (اقرأه أولًا)

هذا الملف هو مدخلي السريع إلى حالة المشروع: ما بنيته، وكيف أبنيه وأشغّله، وما اكتشفته من أخطاء وأصلحته،
وما تبقّى. كل ما فيه جرّبته فعليًا في QEMU، وليس وصفًا نظريًا.

---

## ما هذا المشروع

مشروع نظام تشغيل من الصفر، اسمه **Ghadir OS** (النظام الكامل). يتكوّن من **جزأين في مجلدين**، داخل المجلد الجذر
`ghadir-os/`:

- **`ginux/` — النواة** فقط. هي الجزء الذي يقلع عبر GRUB، وفيه الجدولة (scheduler) والذاكرة المقسَّمة (paging)
  والـ syscalls ونظام الملفات (initrd) وغيرها. كُتبت من الصفر ولا تحمل كودًا من أي نواة أخرى.
- **`gng/` — كل الأدوات** التي تعمل فوق النواة: GCC وglibc وbinutils وTinyCC وdietlibc، مع سكربتات بنائها
  وبرنامج اختبار يشغّلها داخل النواة. (GNG اختصار مازح: *"Ghadir Not GNU"*، تحية لـ *"GNU's Not Unix"*.)
  ومكتبة الـ C الخاصة بي (`libgng`) تنتمي إلى هذا المجلد أيضًا (انظر الملاحظة أدناه).

> **ملاحظة تسمية**: لا يوجد شيء اسمه "Ghadir Kernel"؛ النواة اسمها **ginux** فقط، والنظام الكامل **Ghadir OS**.
> **ملاحظة عن libgng**: مكتبة الـ C الأصلية (`libgng.a` وcrt0 وبرنامج `gng-hello`) لم تكن ضمن الملفات في هذه
> النسخة، فلم تُنقَل إلى `gng/`. حين أدمجها أضعها في `gng/libc/`. و`gng-hello.elf` الموجود في `ginux/` ما زال ملفًا
> جاهزًا بلا مصدر.

أبني المشروع تدريجيًا، مرحلة بعد مرحلة، وأراجع كل كود مراجعة دقيقة، بما فيه الكود الذي أكتبه بنفسي
(اكتشفتُ وأصلحتُ أخطاء حقيقية في كودي أيضًا، انظر §5).

أصل الفكرة فلسفي: كتاب «الاستخلاف: فلسفة إسلامية لبناء نظام تشغيل». كل مبدأ فيه يقابله تطبيق فعلي في الكود
(انظر §9).

## 1. الحالة الحالية (ملخص سريع)

- نواة x86 32-bit مع PAE تقلع عبر GRUB (Multiboot 1) وتعمل في QEMU.
- عزل كامل بين العمليات (page directory منفصل لكل process)، وscheduler من نوع preemptive بتردد 100Hz،
  وW^X حقيقي (NX bit)، وASLR، وstack canaries.
- **البق الرابع (الكرشات المتقطعة بنمط `eip=...FF0`) حُلّ بالكامل بتاريخ 2026-10-03.** سببه الجذري
  كتابة فوق كلمتين حيّتين من stack المهمة المقاطَعة في مقاطعات ring0، وليس عشوائيًا (انظر §6).
  اختبرتُ الاستقرار على أربعة أنواع من المعالجات الافتراضية بلا كرش واحد.
- **مكتبة C حقيقية (GNG)** مبنية وتعمل: `printf` و`malloc` و`free` و`strcpy` و`puts` و`getpid` و`exit`،
  وجرّبتها فعليًا في برنامج ELF32 حقيقي فوق النواة.
- **عزل الأعطال (fault isolation)**: أي bug في برنامج المستخدم (page fault، NULL deref) يقتل هذه العملية
  فقط ولا يُسقط النواة.
- **الـ ABI الأصلي**: 20 استدعاء نظام تعمل (انظر §7)، مع initrd قابلة للكتابة ونافذة أمانة على `unlink`.
- **طبقة التوافق (compat)** (جديدة، 2026-10-03): تسمح لعمليات تتبع واجهة syscalls لمكتبات C القديمة
  (أرقام i386 المعروفة + errno سالب) بالعمل فوق ginux دون المساس بالـ ABI الأصلي (انظر §8). اختبرتُها
  ببرنامج اختبار بلا libc (**42/42 PASS**) وببرنامج C حقيقي مع dietlibc (printf/malloc/fork/waitpid).
- **أربعة تطبيقات فلسفية حقيقية في الكود**: السجل اللارجعي، ومنع الاحتكار بالأقفال، ونافذة الأمانة،
  وفصل الحقائق عن الاعتباريات (انظر §9).
- **مترجمات حقيقية تعمل داخل النواة** (2026-10-12): GCC 4.7.4 وTinyCC وGNU as/ld/objdump، وglibc **حديثة** ساكنة (انظر §17).
- لم أبنِ glibc 2.2 نفسها بعد (لا يوجد مترجم من تلك الحقبة في بيئتي)؛ النواة جاهزة من جهتها (انظر §13).

## 3. البناء والتشغيل

```bash
# المتطلبات (على Linux)
sudo apt install build-essential gcc-multilib grub-pc-bin grub-common xorriso mtools qemu-system-x86 cppcheck

# من جذر المشروع (ghadir-os/):
make help                       # كل الأهداف
make kernel                     # النواة ginux
make test                       # اختبارات النواة على QEMU (تفشل عند أي خطأ، نحو دقيقة)
make toolchain-lite             # dietlibc + tcc + shell (نحو 10 دقائق) ثم make shell لصورة خفيفة
make toolchain                  # + binutils + GCC 4.7.4 (ساعات على معالج واحد)
make run-shell                  # يبني dist/ghadir-os-<الإصدار>.iso ويشغّله
make demo                       # ISO اختبار آلي: النواة + أدوات gng + مشغّل الاختبارات

# داخل ginux/ (للعمل على النواة وحدها):
cd ginux
make clean && make all && make iso                       # ISO بالـ ABI الأصلي (يُشغّل كل اختبارات userland القديمة)
grub-file --is-x86-multiboot ginux.bin                   # تحقق سريع
userland_compat/build.sh && make iso-compat              # ISO بطبقة التوافق (compattest: 83 اختبارًا)
qemu-system-i386 -cpu max -cdrom ginux-compat.iso -display none -serial stdio -no-reboot
make audit                                               # تدقيق النواة (cppcheck)
```

### بناء ISO لأي برنامج يعمل كـ init
`ginux/tools/make-iso-with-init.sh <init.elf> <out.iso> [مجلدات إضافية تُنسخ إلى جذر الـ initrd]`
(البرنامج `init` يُشغَّل وحده عند الإقلاع). وقواعد بناء برامج gng في `gng/README.md`.

- إذا وُجد ملف باسم `init` داخل initrd فإن `kernel_main` يشغّله **وحده** كعملية تابعة لطبقة التوافق
  (بدون عروض الـ ABI القديم). وإلا شغّل العروض القديمة كلها.
- عدّلتُ الـ Makefile ليتتبع تعديلات الـ headers تلقائيًا (`-MMD -MP`). بدون ذلك، تعديل struct في
  `process.h` يترك ملفات `.o` بتخطيط قديم (كان هذا سبب خطأ مزيّف أضاع وقتًا طويلًا).
- لأخذ لقطة شاشة: شغّل QEMU في الخلفية مع `-monitor unix:/tmp/mon.sock,server,nowait` ثم
  `echo "screendump /path/out.ppm" | socat - unix-connect:/tmp/mon.sock` ثم حوّلها بـ `convert`.
  نفّذ ذلك كله في أمر واحد، لأن العمليات التي تعمل في الخلفية تُقتل بين الاستدعاءات المنفصلة.

## 4. التسلسل التاريخي (بالترتيب)

1. بنيتُ النواة الأساسية: Multiboot → GDT → IDT → PIC → PMM → Paging (PAE+NX) → kernel heap → keyboard →
   RNG → stack canaries.
2. أضفتُ: scheduler (preemptive، round-robin)، وعمليات معزولة (page directory منفصل)، وsyscalls (بوابة
   `int 0x80`)، وspinlocks، وELF loader، وpipes (IPC).
3. جرّبتُ الأمان بهجمات تجريبية (out-of-bounds pointer، syscall ممنوع، integer overflow) فصُدّت كلها.
4. كتبتُ بيدي 25 ملفًا لمكتبة C كاملة (كان اسمها "alibc" ثم "mlibc")، وراجعتُ الكود بدقة ووجدتُ أخطاء
   حقيقية (انظر §5) وأصلحتُها، وأصلحتُ النواة لتتوافق معها (ABI الخاص بـ write، و3 استدعاءات جديدة).
5. جرّبتُ end-to-end: `hello.c` (مكتبة C) يعمل فوق النواة بنجاح.
6. أعدتُ التسمية: النواة **ginux**، والأدوات **GNG**، والنظام الكامل **Ghadir OS**، وفصلتُ المجلدين.
7. (2026-07-21) نظام ملفات initrd بصيغة USTAR. (2026-07-28) `fork()` و`waitpid()` حقيقيان.
8. (2026-08-10) السجل اللارجعي، ثم `execve()` حقيقية، ثم منع الاحتكار بالأقفال.
9. (2026-08-11) initrd قابلة للكتابة، ثم نافذة الأمانة. (2026-08-14) فحص شامل للنواة.
10. (2026-08-16) فصل الحقائق عن الاعتباريات. (2026-08-17) argv حقيقي لـ `execve`، ثم مراجعتان خارجيتان عميقتان.
11. (2026-08-18) تنظيف بقايا اسم قديم من الكود. (2026-08-18/23) محاولة إعادة بناء تبديل السياق (لم تُعتمد، انظر §10).
12. (2026-10-03) حل البق الرابع، وإضافة طبقة التوافق، وإثبات تشغيل libc حقيقية فوق النواة.

## 5. أخطاء حقيقية وجدتُها وأصلحتُها (اعرفها قبل أي تعديل)

### 🔴 عزل الأعطال لم يكن موجودًا (النواة)
كانت `isr_handler()` تنفّذ `panic` (إيقافًا كاملًا) عند **أي** استثناء، حتى لو جاء من ring3. أصلحتُها بفحص
`r->cs & 0x3`: إذا كان 3 (ring3) تُقتل العملية المخالفة فقط (`process_kill_current_and_reschedule`) بدل
إيقاف النظام. جرّبتُها بـ NULL pointer dereference حقيقي فنجحت.

### 🔴 `gng/src/syscall.s`: تسريب registers
كانت `__al_syscall1..5` تغيّر `%ebx`/`%esi`/`%edi` بدون `push`/`pop` رغم أنها callee-saved في cdecl، فانكسرت
`sbrk()` (تخزّن `increment` في `%ebx` ثم تنادي `brk()` فتتبدل). النتيجة أن `malloc()` كانت تُرجع عنوانًا
غير mapped فيحدث page fault فورًا. أصلحتُها بحفظ الـ registers واستعادتها.

### 🔴 `gng/src/stdlib.c`: `realloc()` heap buffer overflow
كانت تنسخ الحجم **القديم** كاملًا بدل أصغر القيمتين (القديم/الجديد). عند تصغير `realloc` يفيض النسخ على البلوكة
الجديدة. أُصلحت.

### 🟠 ABI الخاص بـ `write` لم يكن متوافقًا
صمّمتُ `write(fd, buf, len)` على نمط POSIX (`ebx=fd, ecx=buf, edx=len`) بينما كانت النواة القديمة `ebx=ptr,
ecx=len`. أصلحتُ النواة لتتوافق مع GNG، وأصلحتُ كل البرامج القديمة التي كانت تستعمل الـ ABI القديم يدويًا.

### 🟠 أخطاء صغيرة أخرى (كلها مصلحة)
- `unistd.h`: `open()` معلنة variadic لكن مطبقة بثلاثة وسائط ثابتة.
- `stdio.c`: تستعمل `errno` بدون `#include <errno.h>`.
- `mmap.c`: كانت تستعمل `__al_syscall6` غير المعرَّفة؛ أعدتُ كتابتها فوق `sbrk()` (`MAP_ANONYMOUS` فقط).
- `crt0.s`: كانت تنادي `main()` دون ملء `argc`/`argv` (قيم عشوائية من الـ stack).
- `gng/tests/test.ld`: كانت تنتج segment واحدًا **RWX** (تكسر W^X فيرفضها `elf_load()`)؛ أصلحتُها بمحاذاة
  صفحات بين `.text`/`.rodata`/`.data`.
- `Makefile` الخاص بـ GNG: كان يفترض cross-compiler وهميًا؛ صار يستعمل `gcc -m32 -ffreestanding`.

### 🔴 خطأ تغليف: `grub.cfg` مفقود من المشروع (2026-08-14)
كان الـ Makefile ينشئ `iso/boot/grub/` دون أن يضع فيه `grub.cfg`، فأي بناء نظيف لا يقلع أبدًا (GRUB يدخل
شاشة أوامر تفاعلية). كان الخلل مخفيًا لأن ملفًا قديمًا بقي في مساحة العمل. الإصلاح: `grub/grub.cfg` ملف مصدري
متتبَّع يُنسخ في كل بناء.

### 🔴 خطأ تغليف ثانٍ: `execve_target.elf` بلا قاعدة بناء
كان ملفًا جاهزًا دون قاعدة Makefile تعيد بناءه من `userland/execve_target.c`؛ فأي تعديل على المصدر لا يصل إلى
الملف المستعمل في initrd. أُضيفت قاعدة بناء مرتبطة بـ `$(INITRD)`.

### ✅ نتائج نظيفة في الفحص الشامل
cppcheck (warning+style+performance+portability+inconclusive): لا مشاكل حقيقية. `-Wall -Wextra`: صفر تحذيرات
(عدا ملاحظة linker عن `.note.GNU-stack`). كل الملفات المذكورة في الـ Makefile موجودة. و`ptr_in_bounds()`
(بوابة الأمان لكل syscall يلمس ذاكرة المستخدم) سليمة: تفحص overflow أولًا ثم تحصر الوصول في حدود
stack/heap/code الفعلية، بسقف 4096 بايت للعملية الواحدة.

## 6. البق الرابع: قصة التحقيق والحل النهائي

### الأعراض
كرشات متقطعة (`KERNEL PANIC: Page Fault` أو `Division By Zero`) بعد ثوانٍ أو دقائق، وغالبًا مع `eip` ينتهي
بـ `...FF0`، أو `0x0`، أو `0x2D`، وبـ `err=0x10` (محاولة تنفيذ كود، instruction fetch).

### فرضيات جرّبتُها واستبعدتُها (أو تبيّن أنها جزئية)
- خطأ في `fork()`: لا، يحدث بدونه، وبدون ELF، وبدون pipes، وحتى مع kidle وحدها.
- خطأ في تبديل السياق نفسه: جرّبتُ تعطيل `pit_init()` كليًا (بلا IRQ0 من عندي) فبقي الكرش (بعد ~26000
  مجموعة ticks)، لكن IRQ0 كان يعمل رغم ذلك بسبب بقايا إعدادات BIOS (`pic_remap()` كانت تحافظ على قناع BIOS).
- تلف `tasks[0].regs.eip` أو `regs.cs` أو `regs.useresp`: مراقبات hardware watchpoints لم تلتقط شيئًا.
- مسار `terminal_scroll()`: تكرر الكرش مرتين عند `eip=0x101A86` داخلها، لكن فحصًا دفاعيًا داخل الحلقة لم يُطلق
  أبدًا؛ فقد كانت kidle تُقاطَع هناك صدفة لأنها تطبع كثيرًا.
- حجم الـ stack: تكبيره من 8KB إلى 32KB لم يغيّر شيئًا.
- النافذة الزمنية في `scheduler_start()` (BUG #5 القديم): حقيقية، وأُصلحت بـ `cli`، لكنها لم تكن السبب الوحيد.

### لغز `...FF0` (2026-08-15)
كود إنشاء أي عملية يحسب `useresp = stack_vaddr + PMM_FRAME_SIZE - 16` ويساوي دائمًا `...FF0`؛ أي أن العنوان
الذي يقفز إليه المعالج هو **قيمة `useresp` لعملية أخرى** وليس عنوانًا عشوائيًا. وبمراقب شرطي على
`tasks[0].regs.eip` تبيّن أن الحالة المحفوظة لـ kidle سليمة، وأن الـ EIP الحقيقي هو الذي قفز؛ أي أن شيئًا
كتب قيمة `useresp` فوق return address حيّ في stack النواة.

### السبب الجذري (2026-10-03)
مقاطعة same-privilege (ring0→ring0) تدفع المعالج **3 قيم فقط** (eip, cs, eflags) فيكون الـ frame حجمه 56 بايت،
بينما `struct registers` حجمها 64 بايت (فيها `useresp` و`ss`). وكان في الكود موضعان يكتبان على الكلمتين اللتين
تلي الـ frame (وهما أول كلمتين **حيّتين** من stack المهمة المقاطَعة، أي `esp` الأصلي بالضبط):

1. الـ stub في `isr.s` كان ينفّذ `movl $0, 56(%esp)` عند كل مقاطعة ring0 (وكان هذا هو «إصلاح BUG #4» القديم
   الذي وضعتُه ليكون sentinel؛ فتبيّن أنه هو نفسه يُفسد البيانات).
2. `schedule()` كانت تنفّذ `*r = regs` (64 بايت) فوق frame حجمه 56 بايت، فتكتب `useresp` و`ss` فوق stack المهمة.

وعندما تستأنف kidle وتنفّذ `ret` أو `pop` تقرأ قيمة تالفة (غالبًا `useresp` عملية أخرى) فيقع الكرش. وهذا يفسّر
كل الأعراض: النمط `...FF0`، و`err=0x10`، و`eip=0x0` أو `0x2D` عندما كانت الكلمة المكتوبة صفرًا.

### الإصلاح (`boot/isr.s`، ماكرو `BUILD_FRAME`)
عند ring0 نعيد تموضع الـ 14 dword للأسفل بمقدار 8 بايت، فيصير لدينا frame كامل من 16 dword **تحت** `esp` الأصلي
دون المساس بأي بايت حيّ، ونكتب `useresp` = `esp` الأصلي الحقيقي و`ss` = `0x10`. وبذلك يتعامل كل الكود
(`schedule`/`fork`/`execve`/`idt`) مع بنية واحدة موحدة دون sentinel ولا حيل عناوين. وفي الملف نفسه أصلحتُ أن
الرجوع إلى ring3 لا يعيد `es/fs/gs` (كانت تتصفّر عند `iret`، فيسبب أي `rep movs` في كود المستخدم استثناء #GP).

### التحقق
قبل الإصلاح: كرش خلال ثوانٍ في كل التشغيلات. بعده: 0 كرش على `qemu32` و`max` و`Nehalem` و`pentium3`
(عدة تشغيلات لكل معالج)، مع نجاح كل الاختبارات القديمة والجديدة.

### درس
تجنّب sentinels داخل بنية تُكتب فوق stack حيّ. ووحّد شكل الـ trap frame بدل معالجة حالتين مختلفتين.

## 7. الـ ABI الأصلي للنواة (مهم لأي syscall جديد)

```
int 0x80:  eax=رقم النداء, ebx=arg1, ecx=arg2, edx=arg3
```

| # | الاسم | ebx | ecx | edx | الحالة |
|---|---|---|---|---|---|
| 0 | write | fd (1=stdout، 2=stderr، أو fd لملف initrd) | ptr | len | ✅ |
| 1 | pipe_create | -- | -- | -- | ✅ |
| 2 | pipe_write | pipe_id | ptr | len | ✅ |
| 3 | pipe_read | pipe_id | ptr | len | ✅ (non-blocking) |
| 4 | exit | status | -- | -- | ✅ |
| 5 | fork | -- | -- | -- | ✅ حقيقي |
| 6 | execve | pathname ptr | argv ptr | -- | ✅ مع argv حقيقي |
| 7 | waitpid | pid | status_ptr | -- | ✅ (non-blocking) |
| 8 | getpid | -- | -- | -- | ✅ |
| 9 / 10 / 11 / 12 | open / close / read / lseek | -- | -- | -- | ✅ initrd قابلة للكتابة |
| 15 | brk | العنوان الجديد (0 = استعلام) | -- | -- | ✅ heap من 0x44000000 إلى 0x48000000 |
| 20 | **unlink** | pathname ptr | -- | -- | ✅ عبر نافذة الأمانة؛ يرجع handle وليس 0/-1 |
| 21 / 22 | stat / fstat | -- | -- | -- | ✅ |
| 30 | **ledger_read** | index | out_ptr (`ledger_entry_t`) | -- | ✅ قراءة مفتوحة، ولا يوجد syscall للكتابة |
| 31 | **unlink_cancel** | handle | -- | -- | ✅ إلغاء طلب حذف معلّق |
| 32 | **link** | new_path ptr | existing_path ptr | -- | ✅ اسم ثانٍ لنفس المحتوى |
| 13, 14, 16–19, 23–26 | mmap, munmap, gettimeofday, nanosleep, mkdir, rmdir, dup, dup2, chdir, getcwd | -- | -- | -- | ❌ معرَّفة في `al/syscall.h` ولكنها غير مبنية في هذا الـ ABI |

الإجمالي: **20 استدعاء** مبنيًا.

**التحقق الأمني لكل syscall**: أي مؤشر (`ptr`) يجب أن يقع بالكامل داخل منطقة الكود أو الـ stack أو الـ heap
(brk) الخاصة بهذه العملية بالذات (`ptr_in_bounds()` في `src/syscall.c`)، وإلا يُرفض الطلب ويُسجَّل أمنيًا دون
إيقاف النظام.

## 8. طبقة التوافق (compat) — لتشغيل مكتبات C القديمة

### لماذا؟
glibc 2.x القديمة (سنة 2000) مكتوبة على واجهة syscalls لـ i386 المعروفة (`int 0x80`، وأرقام نداءات محددة،
والخطأ يُرجَع كقيمة سالبة `-errno` في eax؛ وglibc تعدّ الخطأ فقط إذا كانت `eax >= 0xfffff001`، وقد
تحققتُ من هذا في مصدر glibc 2.2 نفسه: `sysdeps/unix/sysv/linux/i386/sysdep.h`). **هذه الطبقة ليست كودًا
منقولًا من أي نواة أخرى**؛ هي فقط تلتزم بأرقام النداءات وطريقة إرجاع الخطأ التي كُتبت المكتبة على أساسها.

### التصميم
- الاختيار **لكل عملية**: الحقل `process_t.abi_compat`. العمليات القديمة (gng-hello الجاهز مسبقًا واختباراتي)
  تبقى على الـ ABI الأصلي دون أي تغيير. وكل عملية تُنشأ بـ `process_create_compat` (أو تستدعي `execve` وهي
  تابعة للطبقة) تتبع الواجهة الجديدة.
- القيمة المرجعة: `>= 0` نجاح، و`-errno` فشل. والنداء غير المعروف يرجع `-ENOSYS` مع سطر تشخيصي.
- **الحجب (blocking) بنمط yield & retry**: لا توجد sleep queues في النواة، لذلك عندما لا يكون هناك شيء جاهز
  (قراءة stdin، أو `wait4`، أو pipe، أو `nanosleep`) أُرجِع `eip` بمقدار 2 بايت (ليُعاد تنفيذ `int $0x80`)
  وأعطي المعالج لعملية أخرى. و`eax` وباقي الـ registers تبقى محفوظة.
- stack ابتدائي بـ `argc` و`argv` و`envp` و**`auxv`** (`AT_PHDR`، `AT_PHENT`، `AT_PHNUM`، `AT_PAGESZ`، `AT_BASE`،
  `AT_FLAGS`، `AT_ENTRY`، `AT_UID`…`AT_EGID`، `AT_NULL`).
- stack المستخدم 256KB، و`mmap` من 0x60000000 (تخصيص صاعد)، والتحقق من المؤشرات عبر جداول الصفحات نفسها
  (`PRESENT` + `USER` [+ `WRITE`]) وبأي حجم، وليس عبر سقف 4KB.
- **FPU**: `CR0.EM=0` و`MP` و`NE`، وحفظ/استعادة حالة x87 (`fnsave`/`frstor`) عند كل تبديل سياق
  (glibc تنفّذ `fldcw` فورًا عند البدء).
- `tty.c`: وضع canonical مع echo وbackspace، المدخلات من الكيبورد ومن COM1 (حتى أختبر stdin آليًا).
- تحرير الذاكرة عند الموت (frames وfds، وkernel stack بتأجيل) **لعمليات الطبقة فقط**.
- ربط البرنامج: يجب أن يكون عند 0x40000000 فما فوق (حدود `elf.c`)، وبـ segments منفصلة R-X و RW- (سياسة W^X).
  وprogram headers داخل أول `PT_LOAD` ليعمل `AT_PHDR`. وقد أصلحتُ الـ loader ليدمج الصفحات المشتركة بين
  segments (ويرفض الدمج إذا أعطى W+X).

### النداءات المدعومة (أرقام i386)
`exit`/`exit_group`، `fork`/`vfork`، `read`، `write`، `open`، `close`، `waitpid`/`wait4`، `link`،
`unlink` (عبر نافذة الأمانة)، `execve`، `chdir`، `time`، `lseek`/`_llseek`، `getpid`/`getppid`،
`getuid`/`getgid`/`geteuid`/`getegid` (+نسخ 32)، `kill` (ذاتي فقط)، `dup`، `dup2`، `pipe`، `times`، `brk`،
`ioctl` (`TCGETS`، `TIOCGWINSZ`…)، `fcntl`/`fcntl64`، `getrlimit`/`ugetrlimit`، `gettimeofday`،
`mmap`/`mmap2` (anonymous + ملف خاص)، `munmap`، `mprotect`، `stat`/`lstat`/`fstat` (+`64`، بالتخطيط الحقيقي
64 و96 بايت)، `uname`، `readv`/`writev`، `nanosleep`، `getcwd`، `sigaction`/`sigprocmask` (stubs)، `access`،
وغيرها. كل ما سواها يرجع `-ENOSYS`.
- نداء خاص: **400 = `unlink_cancel(handle)`**. نافذة الأمانة تبقى مفعّلة؛ فعملية الطبقة ترى `unlink` وقد
  «نجح» (يرجع 0)، لكن الحذف الفعلي مؤجَّل ويمكن إلغاؤه.
- الوقت الحقيقي من ساعة CMOS (RTC)، ثم يُحسب بتقدّم ticks.

### الاختبارات
- `userland_compat/compattest.c`: أرقام خام بلا libc. **42/42 PASS** على `qemu32` و`max` و`Nehalem` و`pentium3`،
  وتشمل: errno، `getuid`…، `uname`، `fstat64`، `ioctl TCGETS`، `time`، FPU، `brk`، `mmap`/`mprotect`/`munmap`
  ورفض RWX، ملفات initrd، `fork`+`wait4`+status، القتل بالإشارة (SIGSEGV/SIGABRT)، `pipe` مع EOF، `nanosleep`،
  60 `fork`/`wait` متتالية (كشف تسرب slots وذاكرة وkernel stacks)، و`execve` مع argv/envp/auxv.
- **libc حقيقية**: dietlibc 0.34 (i386، مع تعطيل `WANT_TLS` و`WANT_THREAD_SAFE` و`-fno-stack-protector`) شغّل برنامج
  C فيه `printf` و`malloc(100000)` وقراءة ملف و`fork`+`waitpid` والعمليات العشرية، بلا أي تعديل
  (`gng/dietlibc/build.sh` و`gng/demo/`).

## 10. مكوّنات النواة التي بُنيت على مراحل (ملخص)

- **initrd (USTAR)** (2026-07-21): parser لأرشيف tar عادي يحمّله GRUB كـ `module`. قابل للكتابة منذ
  2026-08-11 (copy-on-write: ملفات الإقلاع تبقى مؤشرات مباشرة، وأول كتابة تنسخ إلى بفر kmalloc). والمجلدات مدعومة منذ 2026-10 (§17). مهم: يجب حجز منطقة initrd في pmm (`pmm_reserve_region`) فور `pmm_init` قبل أي تخصيص آخر.
- **`fork()` و`waitpid()`** (2026-07-28): نسخ كامل لـ address space (كود بصلاحياته الأصلية، stack، heap)، وحالة
  `TASK_ZOMBIE` وحقلا `parent_pid`/`exit_status`. والـ `waitpid` non-blocking (polling) في الـ ABI الأصلي.
  بدون copy-on-write (نسخة كاملة فورية).
- **`execve()`** (2026-08-10): تبني address space جديدة وتحمّل فيها ELF ثم تحرر القديمة، وتعدّل الـ trap frame
  فيعود المعالج إلى بداية البرنامج الجديد. تبنيه في مساحة منفصلة **قبل** مسّ القديمة، فإذا فشل التحميل تبقى
  العملية القديمة كاملة. الـ pid نفسه يبقى (دليل: الاختبار طبع pid=7 قبل `execve` وبعده).
- **argv** (2026-08-17): `build_initial_stack()` تبني `[esp]=argc [esp+4]=argv [esp+8]=envp`. الحد 8 معاملات ×
  64 بايت في الـ ABI الأصلي (و32 معاملًا و32 متغير بيئة في طبقة التوافق). و`envp` فارغة في الـ ABI الأصلي.
- **ثبات هوية الـ fd** (مراجعة خارجية): `fd_entry_t` تخزّن `content_id` (يُحسم مرة واحدة وقت `open()`) بدل index
  الاسم، فلا يتحول fd مفتوح إلى ملف جديد بعد `unlink` وإعادة استعمال الاسم. المحتوى لا يُحرَّر إلا عندما
  يصل `refcount` (الأسماء) و`open_count` (الـ fds المفتوحة) إلى صفر معًا. والتحقق: `fd_identity_test.c`
  (`fd1 correctly kept OLD content -- PASS`).
- **تنظيف التسمية** (2026-08-18): أُزيل اسم قديم ("أطلس") من 118 موضعًا في 11 ملفًا (أسماء ملفات، wrappers،
  رسائل). والبادئة `AL_` في ثوابت syscall تعني Al-Ghadir وبقيت.

## 11. المراجعات الخارجية (2026-08-17): ما وُجد وما أُصلح

**الجولة الأولى (10 نقاط)** كلها مشاكل حقيقية:
- 🔴 P0 البق الرابع: أوصت المراجعة بعدم لمس الـ scheduler قبل حله (وقد أُجِّلت فلسفة «العدالة كتوازن»).
- 🔴 P1 `name[15]='\0'` ناقصة في `process_create_kernel/user/elf` (كانت موجودة في `fork` فقط): أُضيفت.
- 🔴 P1 `initrd_truncate()` ترفع `size` دون التأكد من `capacity` (قراءة خارج الحدود من heap): تستعمل الآن منطق
  النمو نفسه الخاص بـ `initrd_write` مع تصفير البايتات الجديدة.
- 🟠 تخصيصات غير مفحوصة (`pmm_alloc_frame`/`kmalloc`) في أربع دوال: فحص صريح ورسالة وتحرير ما خُصّص سابقًا.
- 🟠 `make audit` يخفي فشل cppcheck (كان status الأمر هو status `tee`): `SHELL := /bin/bash` و`set -o pipefail`.
- 🟡 تحذير compile في `execve_target.c`: `__attribute__((used))`.

**الجولة الثانية (3 نقاط + تحصين الـ ELF)**:
- 🔴 `get_or_create_pd/pt` لا تفحصان فشل التخصيص: ترجعان `NULL`، و`paging_map()` صارت ترجع `int`، وكل
  مواضع الاستدعاء التسعة تفحصها.
- 🔴 `process_create_kernel()` لا يفحص `kmalloc()` للـ kernel stack: أُضيف الفحص.
- 🟠 ELF loader: التحقق من `e_phentsize`، ورفض ELF بلا `PT_LOAD`، والتحقق من `e_entry` داخل segment قابل
  للتنفيذ، وتحرير frame عند فشل `paging_map` أثناء تحميل segment.

**نقاط موثَّقة بلا إصلاح كامل**: rollback متعدد segments عند فشل متأخر في التحميل (تبقى frames سابقة تتسرب)،
وعقد `brk()` (قد يُرجع قيمة محاذاة لصفحة)، وتسرب بنى الـ page tables (لا يوجد `paging_free_address_space`).

التحقق: كل ملفات ELF المضمَّنة حُمِّلت بلا رفض خاطئ، وكل اختبارات التطبيق نجحت في كل التشغيلات.

## 12. محاولة إعادة بناء تبديل السياق (2026-08-18/23) — لم تُعتمد

بعد أن قررتُ «أمسح الكود الذي فيه المشكلة وأبنيه بطريقة جديدة»، جرّبتُ تصميمًا على نمط `swtch()` الكلاسيكي (مثل
xv6): لكل task kernel stack خاصة بها، والتبديل عبر `call`/`ret` الطبيعيين بدل تعديل الـ trap frame يدويًا.

- **اكتشاف مؤكد بالتجربة**: `irq_handler` كانت ترسل `pic_send_eoi()` **بعد** استدعاء الـ handler (وهو
  `schedule()` في حالة IRQ0)، وإذا قفزت `schedule()` قفزة بلا رجوع (إلى `launch_trampoline`) فلا يُرسَل EOI أبدًا
  فيتجمد النظام. الحل أن يُرسَل EOI **قبل** استدعاء الـ handler. وهذا الدرس ما زال صالحًا لأي تصميم مستقبلي.
- ظهرت مشكلتان لم تُحلّا: تعارض مع `-fstack-protector-all` (`STACK SMASHING` حتمي 10/10)، ثم
  `Page Fault` داخل `get_or_create_pt()` بعد تعطيل الحماية كليًا (3–4 كرشات من 5).
- **لم أعتمد التصميم الجديد** وأبقيتُ التصميم القديم. وبعد حل البق الرابع (§6) صار من المحتمل أن بعض هذه المشاكل
  كان مرتبطًا بالسبب الجذري نفسه (كتابة فوق stack مقاطَع)، لكني لم أتحقق من ذلك. وإذا عدتُ إلى هذه المحاولة فنقطة
  البداية: تشخيص `get_or_create_pt()` بـ kprintf/gdb، ثم اختبار استقرار مطوّل (20+ تشغيلة).

## 13. الطريق إلى glibc 2.2 (سنة 2000) ثم GCC

### خارطة الطريق التي وضعتُها وحالة كل خطوة

```
syscall ABI → brk/sbrk + heap → large buffer validation → ELF + auxv
→ file semantics → minimal C runtime → glibc → GNU userspace القديم (binutils، GCC، shell، coreutils)
```

| الخطوة | الحالة |
|---|---|
| تثبيت syscall ABI | ✅ طبقة التوافق (§8): أرقام i386 + `-errno` |
| `brk`/`sbrk` + heap | ✅ بدءًا من 0x44000000، `brk` ترجع القيمة المطلوبة بالضبط في طبقة التوافق |
| التحقق من buffers كبيرة | ✅ في طبقة التوافق (عبر جداول الصفحات، بأي حجم). الـ ABI الأصلي ما زال بسقف 4KB |
| ELF + auxv | ✅ `AT_PHDR`/`AT_PAGESZ`/`AT_ENTRY`… ودمج الصفحات المشتركة بين segments |
| دلالات الملفات | ✅ ملفات وpipes وfds ومجلدات حقيقية (`mkdir`/`rmdir`/`rename`/`getdents`/`chdir`/`getcwd`) في initrd قابلة للكتابة |
| runtime C بسيط | ✅ dietlibc يعمل (printf/malloc/fork/waitpid/FP) |
| glibc 2.2 | ⏳ النواة جاهزة من جهتها، **لم أبنِ المكتبة نفسها** (انظر أدناه) |
| مترجم C يعمل على النواة | ✅ **GCC 4.7.4** و**TinyCC** وGNU **as/ld/objdump** تعمل داخلها (انظر §17) |

### ما تحقّق للتحضير لـ glibc 2.2
راجعتُ مصدر glibc 2.2 الفعلي (`bminor/glibc`، الوسم `glibc-2.2`): بدء البرنامج الساكن يحتاج `getuid`/`geteuid`/
`getgid`/`getegid` (في `__libc_init_secure`)، و`uname` (فحص نسخة النظام)، و`fstat` و`ioctl(TCGETS)` قبل أول
`printf`، و`brk`، و`write`، و`exit`، وauxv، و`fldcw` (FPU). والإصدار 2.2 **لا يستعمل TLS ولا `set_thread_area` ولا
vdso ولا sysenter**، وكلها مدعومة أو غير مطلوبة عندي.

### ما لم يتحقق: بناء glibc 2.2 نفسها
جرّبتُ بـ gcc 13: `configure` يمر (بعد تجاوز فحص إصدارات الأدوات، وتوليد `configure` الفرعية بـ `autoconf2.13`،
وحذف placeholders في `bits/` العليا)، وتتم ترجمة نحو 1550 ملف `.o`، لكن تبقى أخطاء المترجم الحديث:
cast-as-lvalue في `sunrpc/rpc/xdr.h` و`iconv/loop.c` و`msort.c`، وكتل أسمبلي في `sysdeps/i386/dl-machine.h`.
الحل الأنظف: مترجم من الحقبة (gcc 2.95/3.x مع binutils 2.12) عبر `gng/glibc/build-glibc22.sh` (**غير مجرَّب**، مكتوب
ليُشغَّل داخل بيئة من تلك الحقبة، مثل صورة Debian القديمة). بعد البناء: `cp out/hello rootfs_compat/init && make iso-compat`.
ملاحظات للبناء: i486 وليس i686 (لا cmov، لأن `qemu32` و`pentium3` لا يدعمانه)، ولا SSE (النواة لا تحفظ حالته)،
والربط عند `0x40000000` فما فوق وبـ segments منفصلة.

### GCC (تحقّق على إصدار 4.7.4، انظر §17)
بنيتُ GCC 4.7.4 (لغة C فقط) و binutils 2.45 ساكنَين 32-bit وشغّلتهما **داخل ginux**: `gcc` ← `cc1` ← `as` ←
`collect2` ← `ld` ← تشغيل الناتج. أما **GCC حديث (C++ كامل)** فلم أجرّبه بعد، وما زال ينقصه ما ذُكر في §14.

## 14. خارطة الطريق (ما تبقّى، بالترتيب المنطقي)

1. **بناء glibc 2.2** بمترجم من الحقبة وتشغيل `hello` فوق النواة (`gng/glibc/build-glibc22.sh`).
2. **مجلدات حقيقية** في initrd (`mkdir`/`getdents`/`rename`…) ثم توسيع الـ identity map قبل رفع الذاكرة.
3. **إشارات حقيقية** (توصيل handlers، و`kill` بين العمليات، و`sigreturn`) و`select`/`poll`. (الـ shell التفاعلي أُنجز، انظر §18، وما بقي منه: تاريخ الأوامر والأسهم والـ jobs بالخلفية و`2>`.)
4. **تحرير الذاكرة كاملًا**: بنى الـ page tables نفسها (`paging_free_address_space`)، وتعميم تحرير الموارد على
   عمليات الـ ABI الأصلي (الآن لعمليات طبقة التوافق فقط)، مع rollback كامل لفشل التحميل متعدد الـ segments.
5. **GNU userspace**: binutils ثم GCC ثم shell و`make` (انظر §13).
6. **العدالة كتوازن** في الجدولة (الفلسفة)، بعد التأكد من استقرار الـ scheduler.
7. **الطبقة الحديثة**: SMP، وLocal APIC/IOAPIC، وCopy-on-Write، وSlab allocator، وDemand paging.
8. **قابلية إعادة البناء**: يجب أن تدخل `gng-hello.elf` و`stress_fork.elf` في البناء بكود مصدري يُبنى تلقائيًا
   (الآن `gng-hello.elf` جاهز مسبقًا بلا قاعدة بناء من المصدر)، بدل الاعتماد على ملفات ثنائية قديمة.

## 15. حدود معروفة

### الـ ABI الأصلي
- `waitpid` و`pipe_read` non-blocking (polling) ولا توجد sleep queues.
- `fork` بنسخ كامل (بلا CoW)، وكل fd يملك موقعه الخاص بعد `fork` (ليس file description مشتركًا).
- بلا مجلدات (في هذا الـ ABI القديم فقط)، وبلا `$PATH`، وبلا `FD_CLOEXEC`، وargv بحد 8×64.
- تسرب الذاكرة عند خروج العمليات (frames وبنى page tables) في هذا الـ ABI.
- الأرقام المعرَّفة في `al/syscall.h` وغير المبنية: mmap، munmap، gettimeofday، nanosleep، mkdir، rmdir، dup، dup2،
  chdir، getcwd.

### طبقة التوافق
- لا توصيل فعلي للإشارات (handlers لا تُستدعى)، و`kill` يقتل العملية الذاتية فقط.
- لا `select`/`poll`، و`clone` بنمط fork فقط (لا threads)، ولا سكربتات shebang، و`dirfd` حقيقي في عائلة `*at` غير مدعوم (`AT_FDCWD` أو مسار مطلق فقط).
- `mmap MAP_FIXED` غير مدعوم (يلزم لـ ld.so الديناميكي)، و`mremap` يرجع `ENOMEM` (المكتبات تعود لـ malloc+copy)، و`mmap` يخصّص كل الصفحات مسبقًا (لا demand paging).
- كل المستخدمين root (uid/gid دائمًا 0)، وكل fd يملك موقعه الخاص بعد `fork`/`dup`.
- بنى الـ page tables ما زالت تتسرب عند الموت.
- الذاكرة الفيزيائية مدعومة حتى **512MB** (سقف الـ identity map وPMM)؛ جُرّب 300MB مملوءة ومتحقَّق منها تحت `-m 512`.
- `uname` يرجع release=`5.4.0` عمدًا (تمويه توافق): glibc الحديثة ترفض العمل إذا أعلنت النواة إصدارًا أقدم من 3.2.

## 16. تذكيرات لنفسي قبل أي تعديل

- **اختبر فعليًا ولا تفترض**: التجميع النظيف لا يعني runtime صحيحًا. ابنِ ثم ابنِ ISO ثم شغّل QEMU واقرأ سجل
  serial كاملًا قبل أن تقول «يعمل». واختبر على أكثر من `-cpu` (`qemu32`، `max`، `Nehalem`، `pentium3`).
- أوامر QEMU monitor/screendump في أمر واحد (start + sleep + screendump + kill)، وإلا تُقتل العمليات الخلفية.
- **W^X مفروضة على مستوى العتاد**: أي ELF فيه segment كتابة+تنفيذ يُرفض كاملًا. تأكد أن أي linker script جديد يفصل
  الأقسام بمحاذاة صفحات (`userland_compat/compat.ld` مثال).
- **register clobbering في inline asm وأغلفة syscall خطر حقيقي**: دقّق دائمًا في الـ registers المحفوظة.
- **لا تضع sentinels داخل بنية تُكتب فوق stack حيّ** (هذا ما سبّب البق الرابع)، ولا تفترض أن frame المقاطعة بحجم
  `struct registers`: مقاطعة ring0 تدفع 3 قيم فقط.
- لا تعدّل struct مشتركًا في header دون إعادة بناء كل الملفات (الـ Makefile يتتبع التبعيات الآن).
- بقايا الأسماء القديمة (alibc/mlibc) ما زالت في بعض التعليقات والمتغيرات؛ أمر تاريخي غير ضار، وأغيّرها تدريجيًا.
- أي كود جديد يلمس الـ scheduler: أجرِ بعده اختبار استقرار طويلًا (20+ تشغيلة، دقيقة لكل واحدة) على عدة معالجات.

## 17. تحديث 2026-10-12: مجلدات، ذاكرة 512MB، مكتبات حديثة، ومترجمات تعمل على النواة

> ملاحظة: جزء من هذا التحديث (المجلدات في initrd وcwd لكل عملية) كان قد أُضيف إلى الشجرة قبل أن أبدأ هذه الجولة؛
> راجعتُ اختباراته (68 اختبارًا ثم 83) وكلها نجحت، وبنيتُ عليه.

### أخطاء حقيقية في النواة وجدتُها وأصلحتُها
- 🔴 **قناع صفحات 2MB في `paging.c` خاطئ** (من الكود الأصلي): `0xFFFFFFFFC00000` يصلح لصفحات 4MB فيمسح البت 21،
  فكل منطقة 2MB فردية (6MB، 10MB…) كانت تُطابَق على التي قبلها (`0x67A000` ← `0x47A000`) والنواة تكتب على ذاكرة فيزيائية
  خاطئة بمجرد أن يوزّع PMM إطارات فوق 6MB (صفّرتْ page directory عملية حية). القناع الصحيح لـ PAE: `0xFFFFFFFE00000`.
  أُصلح في موضعين (بناء الخريطة و`paging_get_phys`).
- 🔴 **`pdes_needed` يُقرَّب للأسفل**: آخر منطقة 2MB ناقصة من الذاكرة تبقى خارج الـ identity map بينما PMM يوزّع منها،
  فتنهار النواة عند نفاد الذاكرة. صار التقريب للأعلى، ونفاد الذاكرة يرجع `ENOMEM` بهدوء (جُرّب على 64 و128 و200MB).
- 🔴 **inode واحد لكل المجلدات**: `stat` كان يرجع `ino=1` لكل مجلد، و`cpp` في GCC يقارن `st_dev/st_ino` لمجلدات `-I`
  ليحذف المكرر فكان يتجاهل المجلد الثاني ويفشل في إيجاد `stdio.h`. صار لكل مجلد inode فريد (hash من مساره).
- 🟠 تصحيح لما كتبتُه سابقًا في §13: كتبتُ أن سقف الـ identity map هو 128MB (استنتاج خاطئ)؛ الصحيح 512MB.

### ما أُضيف
- **TLS**: `set_thread_area` (مدخل GDT رقم 6، selector `0x33`) تتبدّل قاعدته مع كل عملية، ويرثها `fork`.
- **SSE**: تفعيل `CR4.OSFXSR/OSXMMEXCPT` وحفظ الحالة بـ `fxsave/fxrstor` (512 بايت) عند تبديل السياق، مع الرجوع إلى
  `fnsave` إذا لم يدعم المعالج FXSR. بدونه تنهار glibc الحديثة بـ `#UD` لأنها تختار `strrchr/memcpy` المبنية على SSE2 من CPUID.
- **auxv موسَّعة**: `AT_RANDOM` (16 بايت عشوائية) و`AT_HWCAP` و`AT_CLKTCK` و`AT_SECURE` و`AT_PLATFORM` و`AT_EXECFN`.
- **نداءات جديدة**: عائلة `*at` (`openat`/`mkdirat`/`unlinkat`/`renameat`/`faccessat`/`fstatat64`/`readlinkat`…) بالترجمة إلى
  النداء الأساسي (`AT_FDCWD` أو مسار مطلق فقط)، و`statx` و`AT_EMPTY_PATH`، و`clone` بنمط fork (يرفض threads بـ `ENOSYS`)،
  و`clock_gettime`/`clock_gettime64`/`clock_getres`/`clock_nanosleep`، و`getrandom`، و`prlimit64`، و`sysinfo`، و`futex`
  (عملية واحدة)، و`sched_getaffinity`، و`tkill`/`tgkill`، وعدة stubs صغيرة.
- `uname`: release=`5.4.0` تمويهًا (glibc الحديثة تفحص أن النواة >= 3.2).

### الاختبارات (كلها فعلية على QEMU)
- مجموعة طبقة التوافق: **83/83 PASS** على `qemu32` و`max` و`Nehalem`. الـ ABI القديم: 7 PASS بلا كرش.
- ذاكرة: 300MB تُملأ وتُتحقق بلا أي اختلاف تحت `-m 512`؛ و`ENOMEM` نظيف على الأحجام الأصغر. وتشغيل 200 ثانية بلا كرش.
- **glibc حديثة ساكنة (2.39)**: `printf`، `malloc(300000)`، `fork`+`waitpid`، كتابة/قراءة ملف، أعداد عشرية، stdout سطري صحيح.
- **المترجمات داخل النواة** (`gng/demo/` و`gng/README.md`):
  - TinyCC: ترجم وربط `hello.c` وشغّله (خرج 42).
  - GNU binutils 2.45: `as` ثم `ld` ثم تشغيل الناتج (خرج 9) ثم `objdump -d`.
  - **GCC 4.7.4**: `gcc` ← `cc1` ← `as` ← `collect2` ← `ld` ← تشغيل `/out/hello` (23632 بايت)، خرج 42.

### ملاحظات من التشغيل
- `unlink` لملفات GCC المؤقتة يمر بنافذة الأمانة (3 ثوانٍ تأخير) كما صُمّم؛ لا يضر لكنه يبقي ملفات مؤقتة قليلًا.
- تحذير الاحتكار `process_fork held for ~342M cycles` ظهر مرة عند `fork` بعد تشغيل GCC (العتبة 200M)؛ المعايرة قديمة وتقريبية.
- `cc1` يعمل بصورة 14MB؛ لم أقس أقصى استهلاك ذاكرة لـ GCC على ملف كبير.

### ما لم يتحقق بعد
- GCC **حديث** (C++): لم يجرَّب. و**glibc 2.2** نفسها لم تُبنَ (تحتاج مترجمًا من تلك الحقبة).
- إشارات حقيقية (SIGCHLD وغيرها)، و`select`/`poll`، و`clone` للـ threads، و`mmap` بـ demand paging، و`mremap` حقيقي.
- تحرير page tables (`paging_free_address_space`) وتحرير موارد عمليات الـ ABI القديم.
- لم أجرّب ملفات C كبيرة (آلاف الأسطر) ولا ترجمة GCC لنفسه (self-hosting).

## 18. الـ shell التفاعلي (2026-10-16)

الآن عندي shell تفاعلي يعمل في نافذة QEMU الرسومية (كيبورد PS/2 وشاشة VGA) وعلى serial أيضًا:
`gng/shell/sh.c` (الـ shell) و`gng/shell/cc.c` (غلاف `cc` حول gcc). لبناء ISO التفاعلي: `make shell` (أو `gng/shell/mkiso.sh`).
التشغيل: `qemu-system-i386 -cpu max -m 512 -cdrom dist/ghadir-os-0.01.iso` ثم اضغط داخل النافذة ليلتقط الكيبورد.

### ما يدعمه الـ shell
- أنابيب `|` وتحويل `< > >>` وتسلسل `; && ||` واقتباس `'..' ".."` ومتغيرات `$VAR ${VAR} $? $$` و`~` و`* ?` (في آخر مكوّن من المسار).
  التوسيع يتم **بعد** تنفيذ المقطع السابق بنفس السطر (`false; echo $?` يعطي 1).
- أوامر داخلية: `cd pwd ls [-la] cat echo mkdir [-p] rmdir rm [-rf] undo cp mv touch wc grep head date uptime free uname sleep
  whoami env export unset source . clear true false exit help`. وأي برنامج آخر يُبحث عنه في `PATH` (`/bin`): `gcc cc tcc as ld objdump ar`.
- `cc file.c -o out`: يضيف كل المسارات والخيارات اللازمة لربط البرنامج بـ dietlibc (مع `-c`/`-S`/`-E` لا يضيف مكتبات).
- `undo`: يتراجع عن آخر `rm` خلال نافذة الأمانة (3 ثوانٍ) عبر النداء الخاص 400 مع `-1` (النواة تتذكر آخر مقبض حذف لكل عملية).
- سكربتات: `sh file` و`sh -c "cmd"` و`source file`. وعند الإقلاع يُشغَّل `/etc/profile` (يضبط PATH وHOME ويدخل `/home`).
- أوامر مثل `cd export unset source exit rm undo` تُنفَّذ داخل عملية الـ shell؛ كل الباقي (حتى الداخلي كـ`sleep` و`cat`) بعملية ابن، حتى يعمل Ctrl-C.

### تغييرات النواة اللازمة (كلها في `ginux/`)
- **VGA** (`vga.c`): `\b \r \t` ومؤشر العتاد (CRTC) ومسح الشاشة، وفصل سجلات النواة (`kprintf`) عن شاشة الـ tty: في وضع الـ shell
  تذهب السجلات إلى serial فقط ولا تلوّث الشاشة.
- **الكيبورد** (`keyboard.c`): Ctrl وCaps Lock والمفاتيح الممتدة (تُتجاهل الأسهم)، وShift مع Caps يعطي حروفًا صغيرة.
- **tty** (`tty.c`): الإخراج إلى الشاشة وserial معًا مع فهم `ESC[2J` (مسح) و`ESC[K`؛ والإدخال يُستقبل من **مقاطعة المؤقت** (type-ahead حتى لو
  لا أحد يقرأ)؛ تحرير السطر: Backspace وCtrl-U وCtrl-D (EOF)؛ وأي محرف تحكم آخر يُتجاهل (Ctrl-L كان يدخل السطر فيكسر الأمر التالي).
- **Ctrl-C** (`process_interrupt_foreground`): الـ shell يسجّل `ioctl(0, TIOCSPGRP, -pid_الـshell)`؛ القيمة السالبة = اقتل **أبناء** هذه العملية وكل
  أحفادهم (لا العملية نفسها). الأبناء المباشرون يصيرون zombie (الـ shell يجمع حالتهم: `$?`=130) والأحفاد يُحرَّرون مباشرة. فـ Ctrl-C على `gcc` يقتل
  `cc1` و`as` و`collect2` معه.
- **الجدولة** (`pick_next`): في وضع الـ shell تُجدوَل العمليات التي انتظرت للتو (`yielding`) وkidle **بعد** أي عملية تعمل فعلًا؛ وkidle ينام بـ `hlt`.
  بدون هذا كان kidle يأخذ نصف الوقت أثناء انتظار الـ shell لـ gcc. العلم `yielding` يُصفَّر كل tick.
- **نداءات**: `pipe2` (331) و`dup3` (330) — glibc الحديثة تستعملهما حتى لـ `pipe()` (استعملتُ رقمًا خاطئًا أولًا، 359 هو رقم x86-64).

### حدود معروفة
- **لا تاريخ أوامر ولا أسهم ولا إكمال بـ Tab**: الـ tty في النواة canonical فقط (الأسهم تُتجاهل).
- **لا jobs بالخلفية** (`&` يرفض)، ولا `if/for/while`، ولا aliases، ولا `2>` (تحويل stderr).
- **شاشة VGA النصية لا تعرض العربية** (خط CP437)؛ كل مخرجات الـ shell بالإنجليزية.
- كل الملفات في RAM (initrd): **تضيع عند إغلاق النافذة**. و`rm` يتأخر ~3 ثوانٍ (نافذة الأمانة) فيظهر الملف في `ls` فورًا بعده.
- لا `ps` ولا `kill` ولا `/proc`. ولا إشارات حقيقية: Ctrl-C يقتل مباشرة دون إمكان للبرنامج اعتراضه.
- وجود حالة سباق صغيرة: Ctrl-C لحظة إنشاء الابن قد يفوّته (لم أرَه في الاختبارات).
- مصفوفات `ls` والأنابيب بحدود ثابتة (512 اسمًا، 8 مراحل أنبوب، 64 معاملًا).
